# @openboard/mobile

React Native (Expo SDK 57) app for the spray wall. Phase 2 of `PLAN.md`: wall
onboarding — photograph the wall, map every hold to an LED, verify the map.

Uses `@openboard/aurora-protocol` from this workspace for the wire format, so
the bytes the phone sends are the same ones proven against the hardware.

## Requirements

- **A real Android device.** BLE does not work in an emulator, so the board
  cannot be driven from one. The emulator is only useful for UI work.
- **A dev build, not Expo Go.** `react-native-ble-plx` is native code.
- iOS needs a Mac for the build; nothing in the app is Android-specific.

## Running

```shell
export ANDROID_HOME=$HOME/Android/Sdk
npm run android            # prebuild + gradle + install on the attached device
```

Then for subsequent JS-only changes, `npm start` and reload — a rebuild is only
needed when native dependencies or `app.json` change.

`android/` and `ios/` are generated by `expo prebuild` and are gitignored;
native configuration lives in `app.json`, not in those directories.

  setup.tsx             wall setup: photo, detection, sweep, edit holds
src/

    problem.ts          roles, colours, validation, LED frames — pure, tested
    grades.ts           one scale, Font and V labels — pure, tested
    tick.ts             ascents, consensus grade, stars — pure, tested
    catalog.ts          problem summaries, filtering, sorting — pure, tested

    fit.ts              fitting the photo to its canvas — pure, tested
    db/                 SQLite: schema, migrations, repository — tested on real SQLite
    legacy.ts           one-time import of the old AsyncStorage calibration
    board.ts            BLE: scan, connect, MTU, serialised writes, shared state

`npm test` runs the pure modules and the repository in Node — the repository
against Node's built-in SQLite, so foreign keys and transactions are real.
Anything importing React Native stays out of the test run.

## Editing holds

**Edit holds** shows every hold. Tap one to select it (its LED lights on the
wall if it has one); tap empty wall to add a hold. A tap within 24 screen
pixels of a hold selects it — measured on screen, so zooming in shrinks the
target and lets you add a hold right beside a detected neighbour.

Move the selected hold by dragging the pink crosshair, or with the arrows: a
tap moves it 1.5 screen pixels, a held press repeats. Both scale with zoom, so
zoom in for fine centring. Markers are counter-scaled, so they stay small
instead of covering the hold you are trying to see.

## How calibration works

One pass captures both mappings at once — hold to photo position, and hold to
LED index. The app lights LED *k*, you tap the hold it sits under, it advances.

- **No hold** records a position with nothing beside it, which is different
  from "not yet done" and is kept in the export.
- **Undo** steps back to the last decision and re-lights it.
- Progress autosaves after every decision, so a sweep survives backgrounding.
- **Verify** lights whichever mapped hold you tap.

### Mis-tap detection

Consecutive LED indices sit physically next to each other on the wall — a real
250-LED sweep measured a median jump of 0.052 in normalised coordinates. A hold
far from *both* of its index neighbours is therefore almost certainly a
mis-tap, and the app flags those instead of asking you to check all 250.

The threshold is derived from the wall's own median spacing rather than being a
fixed distance, so it works on a dense spray wall and a sparse one alike.

## Colour fidelity

`src/theme.ts` draws every role colour from the eight that Aurora API 3
reproduces exactly, so what the phone draws is what the wall shows. Picking an
arbitrary colour would quantise — blue has only four levels. See the codec's
README.
